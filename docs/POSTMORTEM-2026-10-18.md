# 2026-10-18 公开复盘：从现有点单网关接入麦当劳

这是对实现记录、首单前复盘和当前代码的公开整理。原始私人复盘、聊天、地址、账号、域名和部署信息未随仓库公开。

## 当前完成度

在原宿主中已经完成增量部署、独立凭据安装、OAuth 接入及 ChatGPT 实际只读调用。ChatGPT 已查到真实门店、菜单和套餐详情；开发阶段也完成了官方只读与非交易计价验证。

**尚未完成首笔真实麦当劳订单的创建、支付、取餐或收到餐品。** 创建成功后实际付款页的行为、真实支付后订单状态与取餐信息，仍需通过首单验证。合成上游里的成功订单、支付状态和取餐码只用于测试。

公开包是从原宿主抽取的参考实现：保留业务状态机、工具白名单、确认保护与持久化；将共享 OAuth 裁为麦当劳单资源，提供通用宿主入口。因此，原部署已通过的检查与公开抽取版本的测试要分别看待。这里没有声称公开包已在另一套生产环境完成交易。

## 真正复用的内容

原系统已经有瑞幸 v4 的 OAuth、逐笔网页批准、落盘 intent 和一次提交模式。本次沿用这些机制，按麦当劳实际工具契约适配，避免在同一私人系统里重建登录和订单框架。

品牌凭据、OAuth Client、Scope、Resource 及订单目录独立。接入时没有把 ChatGPT 的 OAuth Token 当作麦当劳 Token；后者只在服务端注入固定上游。部署采用原设备服务的增量方式，未重启聊天服务。开源版没有携带这些私人部署脚本或旧品牌代码。

## 业务差异造成的实际修正

- 门店查询按实际 Schema 使用收藏，或城市与关键词；没有猜测经纬度参数。收藏路径在一次实际 ChatGPT 调用中失败，城市路径成功，具体失败原因尚未定位。
- 到店首单限制为 `orderType=1`、`beType=1`，不传不属于该类型的业务编码；创建保留实际需要的 `orderType`。
- 套餐轮次来自 `rounds[].id`，请求里按对应字符串轮次组织子项。子项 `maxQuantity=-1` 仍受该轮总量上限约束。
- 特制不能只按商品 code 识别：同一 code 可能通过不同 key 表示标准冰/去冰。服务端补全默认选项，使批准快照对应完整的实际请求。
- 官方响应应核对明确的成功封装；不把 HTTP 200 当作业务成功。使用结构化结果处理带说明文字的文本封装。
- 计价按分处理，创建和查询中的部分金额按元解析。菜单价不能直接充当批准金额。
- 付款采用当次官方 `payH5Url`，没有假设沿用其他品牌的二维码。付款链接通过官方 HTTPS 域名校验；缺失或金额异常时保留已知订单，让本人核实，禁止再建一笔。

## 验证证据应怎样理解

原开发阶段发现了官方工具及必要输入/输出 Schema，完成真实门店、菜单、单品特制、套餐与无冰饮料配置的非交易计价。实际报价只代表当时的门店与商品，未作为长期价格承诺公开。

本公开包的离线测试直接由原定向测试改接宿主装配，覆盖 JSON/SSE 传输、OAuth 资源与权限拒绝、网页身份/Origin/CSRF/nonce、批准过期、价格变化、重复调用、重启、UNKNOWN 阻断和凭据清理。合成测试会模拟“创建”“支付状态”“取餐码”，**所有这些都是虚构测试数据，不是交易凭证**。

真实 ChatGPT 同时查询多个套餐详情曾触发 `MCD_BUSY`。适配器并发上限为 2；顺序读取必要详情即可。这里没有为了避开限制而增加自动建单重试。

## 下一个尚待完成的节点

在自己的部署完成只读与计价后，由本人逐笔批准一笔小额、配置明确的到店订单，亲自支付，再根据官方查询核对状态并实际取餐。只有完成这些步骤，才应将项目状态更新为“真实交易闭环已验收”。

若创建超时或返回不明确，保留 UNKNOWN 与锁记录，先在官方账户核实，不能把首单验收变成重复下单。当前参考实现没有自动对账或管理员一键清理 UNKNOWN 功能。
